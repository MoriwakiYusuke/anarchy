# Proof of Storage Retrieval (PoSR) 技術検討

本ドキュメントでは、Anarchy プロジェクトにおける分散ストレージの検証メカニズム（PoSR）の実現可能性と技術的選択肢について整理する。

## 概要

PoSR は、ストレージノードが実際にデータを保持していることを、データ全体を開示することなく検証可能にする暗号技術である。Anarchy では **Shamir's Secret Sharing (SSS)** と **KZG コミットメント** を組み合わせたアプローチを採用する。

---

## 技術的実現性

### 1. SSS + KZG コミットメントの活用

Ethereum の **EIP-4844 (Proto-Danksharding)** において KZG コミットメントはすでに実用化されている。多項式を用いたデータ検証ロジックは、数千億ドル規模の資産を保護する「枯れた」技術となりつつある。

**実装方針:**

1. データから多項式 $f(x)$ を構成する
2. コミットメント $C = \text{commit}(f)$ をオンチェーンに記録する
3. ノードは断片の保持を証明（Opening Proof）により検証可能

これにより、データの中身を秘匿しながら「正しい断片を保持しているか」を即座に検証できる。

### 2. Tor 経由の P2P 通信

Tor は一般的に遅延が大きいとされるが、テキストや少数の画像といった軽量なストレージ利用であれば実用的な速度が期待できる。

**設計方針:**

- リアルタイム性を要求せず、**非同期（Async）保存**として設計する
- 投稿から数秒後に「保存完了」通知を返すフローで、UX を確保する

### 3. Substrate の最適化

Substrate フレームワークを使用することで、独自の Pallet に KZG 検証ロジックをネイティブ実装できる。

**メリット:**

- バイナリレベルでの高速実行が可能
- 他のチェーンではガス代が問題となる複雑な計算も、Anarchy 専用チェーンでは最適化可能
- Rust による低レベル制御

---

## 技術的課題

### 1. Trusted Setup（信頼できるセットアップ）

KZG コミットメントには、初期化時に「誰も知らない秘密の値 $s$」を用いてパラメータを生成する儀式（Ceremony）が必要となる。

**選択肢:**

| 方式 | 特徴 | トレードオフ |
|------|------|--------------|
| KZG + Trusted Setup | 計算効率が高い | セットアップの信頼性が必要 |
| IPA (Inner Product Argument) | Trustless（信頼不要） | 計算コストがやや高い |

### 2. ノード数の確保

Tor 経由の通信は、ノード数が少ないと不安定になりやすい。サービス開始初期におけるノード運営者の確保が課題となる。

---

## 推奨アプローチ: Ethereum KZG Ceremony の流用

Trusted Setup の課題に対し、最も効率的な解決策は **Ethereum の KZG Ceremony 成果物を流用**することである。

### 背景

KZG コミットメントに使用されるパラメータ（SRS: Structured Reference String）は、特定のブロックチェーン専用ではない。同一の楕円曲線（Curve）を使用する場合、他のプロジェクトが実施した儀式の結果をそのまま再利用できる。

### Ethereum KZG Ceremony

- 数万人が参加し、秘密値 $s$ の破壊を厳重に実施
- 成果物（Powers of Tau ファイル）は公開されており、誰でもダウンロード可能

### メリット

| 観点 | 説明 |
|------|------|
| **信頼性** | 単一プロジェクトではなく、Ethereum Foundation と数万人の参加者による保証 |
| **実装コスト** | パラメータをダウンロードして Substrate チェーンに組み込むだけ |
| **思想的整合性** | 既存の大規模インフラを再利用するアプローチは Anarchy の分散理念とも合致 |

### 技術要件

- 楕円曲線: **BLS12-381** を使用すること
- パラメータファイル: Ethereum の Powers of Tau をそのまま利用可能

---

## 結論

PoSR の実現に必要な技術基盤は確立されている。

**推奨実装パス:**

1. **KZG コミットメント** を採用（計算効率優先）
2. **Ethereum KZG Ceremony** の成果物を流用（Trusted Setup 問題の回避）
3. **BLS12-381** 曲線を使用
4. Substrate Pallet として検証ロジックをネイティブ実装
