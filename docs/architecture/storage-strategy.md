## 2. 設計思想: 地図と宝

### 2.1 比喩

```
┌─────────────────────────────────────────────────────────────┐
│                     バリデーター（脳）                        │
│                                                             │
│   「宝の地図」だけを保持                                      │
│   - 投稿ID                                                   │
│   - 作成者ハッシュ                                            │
│   - 断片ロケーション（どのストレージノードが持つか）            │
│   - 報酬配分ロジック                                          │
│                                                             │
│   本文は一切持たない → 法的要求に「提出不能」                  │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ 参照
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   ストレージノード（体）                      │
│                                                             │
│   「宝」＝暗号化された断片を保持                               │
│   - SSS で分割された断片                                      │
│   - 単体では意味をなさない                                    │
│   - 報酬と引き換えに保持を継続                                │
│                                                             │
│   復号鍵を持たない → 内容を知ることが不可能                    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 原則

1. **バリデーターは本文を持たない**: メタデータ（地図）のみ
2. **ストレージノードは鍵を持たない**: 暗号化断片（宝）のみ
3. **クライアントだけが完全な情報を持つ**: 暗号化・復号はすべてローカル

## 3. 技術構成

### 3.1 SSS（Shamir's Secret Sharing）

投稿本文を数学的に断片化：

```
原文 "Hello, World!"
    │
    ▼ クライアント側で暗号化
暗号文 (ChaCha20-Poly1305)
    │
    ▼ SSS で分割 (k=3, n=5)
┌───┬───┬───┬───┬───┐
│ S1│ S2│ S3│ S4│ S5│  ← 5つの断片
└───┴───┴───┴───┴───┘
  │   │   │   │   │
  ▼   ▼   ▼   ▼   ▼
 Node Node Node Node Node
  A    B    C    D    E

復元には任意の3断片が必要
```

**パラメータ:**
- `n` (総断片数): 保存先ノード数
- `k` (閾値): 復元に必要な最小断片数
- 推奨: `k = ceil(n * 0.6)` (過半数 + α)

### 3.2 Proof of Spacetime

ストレージノードが断片を実際に保持していることを検証：

```rust
// ストレージノードは定期的に証明を提出
fn prove_storage(
    fragment_id: FragmentId,
    challenge: Challenge,
    proof: SpacetimeProof,
) -> Result<(), Error>;
```

証明に失敗したノード → 報酬停止 → 断片を他ノードに再配布

### 3.3 経済的忘却

```
投稿の寿命 = Σ(ステーク報酬) - Σ(ストレージコスト)

報酬 > コスト → 断片は保持され続ける
報酬 < コスト → 断片は「忘却」される
```

誰も注目しない（リアクションがない）投稿 → 経済的に消滅

## 4. データフロー

### 4.1 投稿作成 → **実装済み** (2026-02-10)

```
1. ユーザーが投稿を作成
2. フロントエンド (Web Worker + Wasm) が SSS で断片化
   - sharks crate を Wasm にコンパイル
   - k=3, n=5 で分割（システム固定値）
3. Merkle Tree 構築
   - 断片から merkle_root を計算
   - fragment_id = hash(merkle_root || index)
4. ブロックチェーンノードの RPC 経由でストレージノードへ断片アップロード
   - storage_uploadFragment RPC
5. メタデータをチェーンに登録 (Post Pallet V2)
   - create_post_v2(merkle_root, fragment_count)
6. $moral を支払い
```

### 4.2 投稿閲覧 → **実装済み** (2026-02-10)

```
1. チェーンからメタデータを取得 (merkle_root, fragment_count)
2. fragment_id を計算: hash(merkle_root || index) for i in 0..n
3. k 個以上の断片をストレージノードから取得
   - storage_getFragment RPC
4. SSS で復元 (Web Worker + Wasm)
5. 表示
```

### 4.3 投稿削除（経済的忘却）

```
1. 投稿者がストレージ報酬の支払いを停止
2. ストレージノードにとって保持が赤字に
3. 断片を破棄（経済的に合理的な選択）
4. k 個未満になると復元不可能に
5. 投稿は実質的に「忘却」される
```

## 5. 否認可能性（Plausible Deniability）

### 5.1 法的要求への対応

```
当局: 「投稿 #12345 の本文を提出せよ」

バリデーター: 「我々はメタデータ（断片の場所）しか持っていません」

ストレージノード: 「我々は暗号化された断片を持っていますが、
                   復号鍵がないため内容は不明です」

クライアント: 「?」（オフライン / 匿名 / 複数国に分散）
```

### 5.2 技術的担保

- バリデーターのストレージに本文が存在しないことは、ランタイムコードで検証可能
- ストレージノードが保持するのは暗号化断片のみ（復号鍵なし）
- クライアントは Tor 経由で匿名

### 8.1 将来の最適化案: 圧縮 → SSS

**現状の問題**:
- SSS (k=3, n=5) は元データの約1.67倍のストレージを消費
- テキスト投稿は圧縮しやすいが、現状は非圧縮でそのまま分割

**解決策**: SSS前に圧縮を挟む

```
元データ → gzip/zstd圧縮 → SSS分割 → 断片
断片 → SSS復元 → gzip/zstd展開 → 元データ
```

**期待効果**:
- テキストなら30-70%圧縮可能 → 実効ストレージ効率が大幅改善
- 例: 1KB投稿 → 圧縮後300B → SSS後500B (元の0.5倍)

**実装方針**:
- ブラウザ標準の `CompressionStream` (gzip/deflate) を使用
- または `fflate` ライブラリ (zstd未サポート、gzip/deflateのみ)
- Wasm側で `flate2` crate を使う選択肢もあり

**セキュリティ考慮**:
- 圧縮後のサイズから元データの特性が推測される可能性あり
- パディングで固定サイズに揃える対策も検討

**優先度**: 低（機能より効率の問題）

- **技術構成**: Pallet 側で `nonce` と `difficulty` を管理し、フロントエンドの Web Worker で `hash` を回す

### 13.3 DM（1対1）：ステルスアドレス + E2EE

特定の 1 人にだけ送る場合は、[memo.md](../vision/critique.md) に記載のステルスアドレス・プロトコルを使用。

```
送信者 ──[X25519鍵交換]──> 一時的な共有秘密
                              │
                              ▼
              ┌────────────────────────────┐
              │  ChaCha20-Poly1305 で暗号化 │
              │  ステルスアドレス宛に送信    │
              └────────────────────────────┘
```

#### 秘密鍵のペアダンス（詳細）

DMでも「相手が見れる」必要があるが、原理は同じ。

```
┌─────────────────────────────────────────────────────────────────┐
│                    DM 鍵交換プロセス                             │
│                                                                 │
│  1. 鍵の合成                                                     │
│     送信者: 自分の秘密鍵 × 相手の公開鍵 → 共有鍵 S               │
│                                                                 │
│  2. 暗号化                                                       │
│     メッセージを共有鍵 S で暗号化                                 │
│     → 暗号化後、鍵 S は捨てる（メモリから消去）                   │
│                                                                 │
│  3. 送信                                                         │
│     暗号文 + エフェメラル公開鍵をチェーンへ                       │
│     ※ 共有鍵 S 自体はネットワーク上に一度も流れない              │
│                                                                 │
│  4. 受信者の復号                                                  │
│     受信者: 自分の秘密鍵 × 送信者の公開鍵 → 共有鍵 S（再現）      │
│     → 全く同じ鍵を手元で生成し、復号                             │
└─────────────────────────────────────────────────────────────────┘
```

**重要**: ネットワーク上には一度も「解読できる状態の鍵」は流れない。秘密鍵という「マスターキー」を本人が持っているからこそできる。

### 13.5 管理者（ノード運営者）が中身を見れない理由

ストレージノード運営者が中身を見れないのは、彼らが **「鍵を拾いに行って、組み立てて、解読する」という能動的な行為** をシステム的に禁止（あるいは機能として排除）されているから。

```

│  保持しているもの                          │
│  ├── 断片 #1 (意味不明なバイト列)          │

│  ├── 復号鍵 (チェーン上にあるが参照しない) │
```

#### 13.5.1 フルストレージノード問題（重要な例外）

> **「全断片を持っているノードがいたら、筒抜けやん」**

これは正しい指摘。**フルストレージノード**（全ての断片を保持するノード）は理論上、全ての公開投稿を復元・復号可能。

```
フルストレージノードの視点:

┌───────────────────────────────────────────┐
│  保持しているもの                          │
│  ├── 断片 #1 ✓                            │
│  ├── 断片 #2 ✓                            │
│  ├── 断片 #3 ✓                            │
│  ├── 断片 #4 ✓                            │
│  └── 断片 #5 ✓  ← k個以上揃っている！      │
│                                           │
│  チェーンから取得可能                       │
│  ├── 復号鍵 (公開投稿の場合)               │
│  └── 断片の対応関係                        │
└───────────────────────────────────────────┘

結論: 「見ようと思えば見れる」し「見る能力もある」
       → 公開投稿は筒抜け
```

**リスク評価:**

| 投稿タイプ | フルノードへのリスク |
|-----------|-------------------|
| **公開投稿** | **高**: 鍵も公開されているため完全に復元可能 |
| **フォロワー限定** | **低**: 復号鍵がフォロワーの公開鍵で暗号化されているため、フルノードでも復号不可 |
| **DM** | **なし**: ステルスアドレス + E2EE により完全に保護 |

**対策案:**

1. **断片配布の分散強制**
   - 同一オペレーターへの断片集中を禁止
   - 断片配布先をランダム化（地理的・論理的に分散）
   
   ```rust
   // 断片配布時のバリデーション
   fn validate_distribution(shards: &[ShardLocation]) -> Result<(), Error> {
       let unique_operators = shards.iter()
           .map(|s| s.operator_id)
           .collect::<HashSet<_>>();
       
       // 最低でも k 個以上の異なるオペレーターに分散
       ensure!(unique_operators.len() >= threshold, Error::InsufficientDistribution);
       Ok(())
   }
   ```

2. **経済的ディスインセンティブ**
   - 全断片保持は膨大なストレージコストがかかる
   - 報酬は「保持している断片数」に比例するので、全部持つメリットが薄い
   
   ```
   コスト:  全断片保持 = O(全投稿数 × 断片サイズ)
   報酬:    断片あたりの報酬 × 保持断片数
   
   → 全部持っても報酬は増えるが、コストも比例して増える
   → 「覗き見」のためだけに赤字を垂れ流す動機は低い
   ```

3. **運用的な現実**
   - ネットワーク規模が大きくなると、全断片保持は物理的に困難
   - Filecoin や IPFS でも同様の問題は存在するが、規模で緩和
   
   ```
   投稿数: 100万件
   断片数: 5断片/投稿
   断片サイズ: 1KB
   
   全断片保持 = 100万 × 5 × 1KB = 5GB（まだ現実的）
   
   投稿数: 10億件（Twitter規模）
   全断片保持 = 5TB（個人には厳しい）
   ```

**結論:**

> **「完璧な防御は存在しない。公開投稿はフルノードに見られる可能性がある。本当に隠したいならフォロワー限定か DM を使え。」**

これは「公開」の意味を正しく理解した上での設計。公開投稿は「誰でも見れる」のが仕様であり、フルノードに見られても問題ないデータのみを公開すべき。

> **「秘密鍵は、君の魂の印鑑。それをブラウザの外に出さない限り、Anarchy の世界では君の秘密は絶対不可侵の領域に守られる。」**

### 14.1 なぜノード運営者は「鍵」すら見つけられないか

非公開投稿の場合、フルストレージノード保持者でも以下の絶望を味わう：

```
┌─────────────────────────────────────────────────────────────────┐
│               フルノード運営者の絶望                              │
│                                                                 │
│  1. 地図はあるが宝箱が透明                                        │
│     → チェーンを見ても「鍵」の欄が空っぽ（または無意味なハッシュ） │
│                                                                 │
│  2. 宝箱を拾っても開かない                                        │
│     → 運良く断片を集めて箱を組み立てても、                        │
│       鍵穴が「暗号学的なブラックホール」                          │
│                                                                 │
│  3. 誰の宝箱かも不明                                              │
│     → ステルスアドレスを使っていれば、                            │
│       それが誰宛ての箱なのかすら判別不可能                        │
└─────────────────────────────────────────────────────────────────┘
```

**結論**: 管理者がどうこうできる余地を「数学」で物理的に消し飛ばしている。

### 14.2 秘密鍵のブラウザ内保管

秘密鍵をブラウザ内でどう安全に保管するか。

#### オプション A: 暗号化 Keystore ファイル

```typescript
// キーストアの構造
interface EncryptedKeystore {
  version: 1;
  crypto: {
    cipher: 'chacha20-poly1305';
    ciphertext: string;      // 暗号化されたシードフレーズ
    nonce: string;
    kdf: 'argon2id';
    kdfparams: {
      memory: 65536;         // 64MB
      iterations: 3;
      parallelism: 4;
      salt: string;
    };
  };
  address: string;           // AccountId（検証用）
}
```

**フロー:**
```
パスワード入力
    │
    ▼ Argon2id (メモリハード KDF)
派生鍵
    │
    ▼ ChaCha20-Poly1305
シードフレーズを暗号化
    │
    ▼ IndexedDB に保存
```

**メリット:**
- パスワードなしでは秘密鍵を取り出せない
- メモリハード KDF でブルートフォース耐性

**リスク:**
- 悪意あるフロントエンドがパスワード入力時に盗聴可能
- → ブラウザ拡張ウォレット連携で緩和（[development/todo.md](../development/todo.md) 参照）

#### オプション B: ブラウザ拡張ウォレット連携

```
┌─────────────────┐     ┌─────────────────┐
│   フロントエンド  │     │  Talisman 等    │
│   (Next.js)     │ ──→ │  拡張ウォレット   │
│                 │     │                 │
│  署名リクエスト   │     │  秘密鍵は       │
│  のみ送信        │     │  ここで管理      │
└─────────────────┘     └─────────────────┘
```

**メリット:**
- フロントエンドは秘密鍵に一切触れない
- ハイドラ戦略との相性抜群（どのフロントを使っても安全）

**実装**: PAPIの `@polkadot-api/pjs-signer` で連携可能

### 14.3 ソーシャル・リカバリー（構想）

> **「秘密鍵を紛失した時に、フォロワーの助けを借りてアカウントを復旧する」**

秘密鍵を紛失した場合、通常は全てのデータにアクセス不能になる。ソーシャル・リカバリーはこれを緩和する仕組み。

#### 仕組み

```
┌─────────────────────────────────────────────────────────────────┐
│                  ソーシャル・リカバリー設定時                      │
│                                                                 │
│  1. リカバリー用の秘密 R を生成                                    │
│                                                                 │
│  2. R を SSS で分割（例: 5人中3人で復元可能）                       │
│     ┌───┬───┬───┬───┬───┐                                       │
│     │ S1│ S2│ S3│ S4│ S5│                                       │
│     └───┴───┴───┴───┴───┘                                       │
│       │   │   │   │   │                                         │
│       ▼   ▼   ▼   ▼   ▼                                         │
│     友人A 友人B 友人C 友人D 友人E                                  │
│     (それぞれの公開鍵で暗号化して配布)                              │
│                                                                 │
│  3. R で暗号化された「アカウント移行用の情報」をチェーンに保存       │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                  リカバリー実行時                                 │
│                                                                 │
│  1. 新しいデバイスで新しい鍵ペアを生成                             │
│                                                                 │
│  2. 友人 3人以上に連絡し、断片を送ってもらう                       │
│     (友人は自分の秘密鍵で復号して断片を渡す)                        │
│                                                                 │
│  3. 断片を結合して R を復元                                        │
│                                                                 │
│  4. R で「アカウント移行用の情報」を復号                           │
│                                                                 │
│  5. 新しい鍵ペアでアカウントを再構築                               │
└─────────────────────────────────────────────────────────────────┘
```

#### 制限事項

| 復旧可能 | 復旧不可能 |
|---------|-----------|
| Identity（アカウント自体） | 「自分だけ」の投稿（鍵が失われているため） |
| フォロワー関係 | 過去のDM履歴 |
| 公開投稿へのアクセス | 秘密鍵で派生した全ての暗号化データ |

**注意**: ソーシャル・リカバリーは「アカウントの継続性」を保証するが、「過去の非公開データ」は原理的に復旧不可能。これは機能ではなく、暗号学的な限界。

#### 設計上の懸念

- **共謀リスク**: 友人が結託して不正に復旧を試みる可能性
  - → 緩和策: タイムロック（リカバリー要求後 7日間の待機期間）
  - → 緩和策: 本人への通知（元の鍵でキャンセル可能）
  
- **友人の鍵紛失**: 友人が自分の秘密鍵を紛失したら断片が取り出せない
  - → 緩和策: 十分な冗長性（5人中3人など）

## 15. 結論: 技術がプライバシーの「物理法則」になる

```
┌─────────────────────────────────────────────────────────────────┐
│                    Anarchy の防衛戦略                            │
│                                                                 │
│  Layer 1: ネットワーク匿名性                                      │
│           └── Tor + libp2p (IP アドレス匿名化)                    │
│                                                                 │
│  Layer 2: データ断片化                                            │
│           └── SSS (k-of-n 分割、単体では無意味)                   │
│                                                                 │
│  Layer 3: 暗号化                                                  │
│           └── ChaCha20-Poly1305 (復号鍵なしでは解読不可)          │
│                                                                 │
│  Layer 4: 鍵管理                                                  │
│           └── 公開: チェーン上に鍵公開                            │
│           └── 限定: 受信者の公開鍵で鍵を暗号化                    │
│           └── DM: ECDH で共有秘密を生成                           │
│           └── 自分: ローカルにのみ鍵を保存                        │
│                                                                 │
│  Layer 5: 経済的忘却                                              │
│           └── 報酬停止 → データ消滅                              │
└─────────────────────────────────────────────────────────────────┘
```

> **「正解の鍵を世界中のどこにも置かない」という究極の引きこもり戦略が、最強の防御になる。**
