## 1. 現状の問題

### 1.1 オンチェーンストレージの限界

現在の `pallet-post` は投稿本文を直接オンチェーンに保存している：

```rust
#[pallet::storage]
pub type Posts<T: Config> = StorageMap<_, Blake2_128Concat, PostId, Post<T>>;

pub struct Post<T: Config> {
    pub author: T::AccountId,
    pub content: BoundedVec<u8, T::MaxContentLength>,  // ← 本文がここに
    pub created_at: BlockNumberFor<T>,
}
```

**問題点:**
- ストレージ容量に上限がない（スパム攻撃に脆弱）
- バリデーターが全投稿本文を保持（プライバシーリスク）
- 「忘れられる権利」を実装不可能（ブロックチェーンは不変）
- 法的要求に対してバリデーターが本文を提出可能

## 2. 設計思想: 地図と宝

### 2.1 比喩

```
┌─────────────────────────────────────────────────────────────┐
│                     バリデーター（脳）                        │
│                                                             │
│   「宝の地図」だけを保持                                      │
│   - 投稿ID                                                   │
│   - 作成者ハッシュ                                            │
│   - 断片ロケーション（どのストレージノードが持つか）            │
│   - 報酬配分ロジック                                          │
│                                                             │
│   本文は一切持たない → 法的要求に「提出不能」                  │
└─────────────────────────────────────────────────────────────┘
                              │
                              │ 参照
                              ▼
┌─────────────────────────────────────────────────────────────┐
│                   ストレージノード（体）                      │
│                                                             │
│   「宝」＝暗号化された断片を保持                               │
│   - SSS で分割された断片                                      │
│   - 単体では意味をなさない                                    │
│   - 報酬と引き換えに保持を継続                                │
│                                                             │
│   復号鍵を持たない → 内容を知ることが不可能                    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 原則

1. **バリデーターは本文を持たない**: メタデータ（地図）のみ
2. **ストレージノードは鍵を持たない**: 暗号化断片（宝）のみ
3. **クライアントだけが完全な情報を持つ**: 暗号化・復号はすべてローカル

## 3. 技術構成

### 3.1 SSS（Shamir's Secret Sharing）

投稿本文を数学的に断片化：

```
原文 "Hello, World!"
    │
    ▼ クライアント側で暗号化
暗号文 (ChaCha20-Poly1305)
    │
    ▼ SSS で分割 (k=3, n=5)
┌───┬───┬───┬───┬───┐
│ S1│ S2│ S3│ S4│ S5│  ← 5つの断片
└───┴───┴───┴───┴───┘
  │   │   │   │   │
  ▼   ▼   ▼   ▼   ▼
 Node Node Node Node Node
  A    B    C    D    E

復元には任意の3断片が必要
```

**パラメータ:**
- `n` (総断片数): 保存先ノード数
- `k` (閾値): 復元に必要な最小断片数
- 推奨: `k = ceil(n * 0.6)` (過半数 + α)

### 3.2 Proof of Spacetime

ストレージノードが断片を実際に保持していることを検証：

```rust
// ストレージノードは定期的に証明を提出
fn prove_storage(
    fragment_id: FragmentId,
    challenge: Challenge,
    proof: SpacetimeProof,
) -> Result<(), Error>;
```

証明に失敗したノード → 報酬停止 → 断片を他ノードに再配布

### 3.3 経済的忘却

```
投稿の寿命 = Σ(ステーク報酬) - Σ(ストレージコスト)

報酬 > コスト → 断片は保持され続ける
報酬 < コスト → 断片は「忘却」される
```

誰も注目しない（リアクションがない）投稿 → 経済的に消滅

## 4. データフロー

### 4.1 投稿作成

```
1. ユーザーが投稿を作成
2. クライアント (Wasm) が暗号化
3. クライアントが SSS で断片化
4. 各断片をストレージノードに送信
5. メタデータをチェーンに登録 (Storage Pallet)
6. $moral を支払い
```

### 4.2 投稿閲覧

```
1. チェーンからメタデータを取得
2. 断片ロケーションを確認
3. k 個以上の断片をストレージノードから取得
4. SSS で復元
5. クライアントで復号
6. 表示
```

### 4.3 投稿削除（経済的忘却）

```
1. 投稿者がストレージ報酬の支払いを停止
2. ストレージノードにとって保持が赤字に
3. 断片を破棄（経済的に合理的な選択）
4. k 個未満になると復元不可能に
5. 投稿は実質的に「忘却」される
```

## 5. 否認可能性（Plausible Deniability）

### 5.1 法的要求への対応

```
当局: 「投稿 #12345 の本文を提出せよ」

バリデーター: 「我々はメタデータ（断片の場所）しか持っていません」

ストレージノード: 「我々は暗号化された断片を持っていますが、
                   復号鍵がないため内容は不明です」

クライアント: 「?」（オフライン / 匿名 / 複数国に分散）
```

### 5.2 技術的担保

- バリデーターのストレージに本文が存在しないことは、ランタイムコードで検証可能
- ストレージノードが保持するのは暗号化断片のみ（復号鍵なし）
- クライアントは Tor 経由で匿名

## 10. 実現可能性の評価

> **結論: 技術的には可能だが、ストレージレイヤーはボス級の難易度**

特に **Proof of Spacetime (PoST)** と **自己修復プロトコル** は、Filecoin や Arweave といった巨大プロジェクトが数年かけて磨き上げた領域。Substrate で一から組むのはかなりエキサイティングな挑戦になる。

### 10.1 Storage Pallet & Node（難易度: 鬼）

Anarchy プロトコルの「体」になる部分。

| 機能 | 実現可能性 | 懸念点・アドバイス |
|------|------------|-------------------|
| **PoST 検証** | 可能 | オンチェーンでの検証は計算コストが高いため、**Off-chain Workers (OCW)** を使って検証の重い部分を逃がす設計が必須 |
| **自然な忘却** | **最高** | 哲学的に面白い。報酬（$moral）が切れたらデータが消えるのは、「価値のない情報は消え、誰かが愛でる情報だけが残る」というアナーキーな記憶の形 |
| **libp2p 受信** | 可能 | Tor 経由での大容量データ転送はノードの負荷が高い。ストレージ専用の `libp2p` 接続制限を設けないと、バリデーターの合意形成を邪魔するリスクあり |

### 10.2 PoW Faucet（難易度: 低〜中）

今すぐにでも実装できる **「クイックウィン」** な機能。

- **ボット対策**: 数十秒の PoW は、ユーザー体験を損なわずにシビル攻撃（大量のアカウント作成）を防ぐのに有効
- **匿名性の担保**: IP 制限をかけずに「計算量」だけで初期トークンを配るのは、Tor 前提の Anarchy と相性抜群
- **技術構成**: Pallet 側で `nonce` と `difficulty` を管理し、フロントエンドの Web Worker で `hash` を回す

### 10.3 自己修復プロトコルの罠

k-of-n（消失訂正符号）を使った再配布は、理論は完璧だが実装でハマりやすいポイントがある。

> **「ノードが 1 台死ぬたびに全ネットワークで再配布が走ったら、トラフィックが爆発してパンクする」**

これを防ぐには、**「閾値を下回った時だけ、インセンティブ付きで再配布を募集する」** という、スローで自律的なトリガーにする必要がある。

## 13. 鍵配布戦略（公開範囲別）

> **「データは世界中にバラバラに捨てられているけど、それをつなぎ合わせて『意味』に変えるための魔法（鍵）は、プロトコル上のルールに従った人だけが手に入れられる。」**

「自分しか鍵を持っていなかったら、自分専用のメモ帳になってしまう」という疑問への回答。

### 13.1 公開投稿：鍵を「看板」にぶら下げる

誰でも見れる投稿の場合、**復号するための鍵（AES鍵）もセットで公開** する。

```
┌─────────────────────────────────────────────────────────────────┐
│                        公開投稿のフロー                          │
│                                                                 │
│  1. 投稿者                                                       │
│     │                                                           │
│     │ 投稿内容を AES鍵 (Key_A) で暗号化                           │
│     ▼                                                           │
│  ┌─────────────────┐                                            │
│  │  暗号化された本文  │ ─── SSS分割 ──→ ストレージノードへ         │
│  └─────────────────┘                                            │
│                                                                 │
│  2. メタデータ（チェーン上）                                       │
│     ┌─────────────────────────────────────────┐                 │
│     │  PostId: 12345                          │                 │
│     │  FragmentLocations: [Node1, Node2, ...] │                 │
│     │  DecryptionKey: Key_A  ← ★公開！        │                 │
│     └─────────────────────────────────────────┘                 │
│                                                                 │
│  3. 閲覧者                                                       │
│     │                                                           │
│     │ チェーンから Key_A を取得                                   │
│     │ ストレージノードから断片を収集                               │
│     │ SSS復元 → Key_A で復号                                     │
│     ▼                                                           │
│  ┌─────────────────┐                                            │
│  │    平文の投稿     │                                            │
│  └─────────────────┘                                            │
└─────────────────────────────────────────────────────────────────┘
```

**「鍵を公開したら暗号化の意味がない？」** → ここがミソ：

| 視点 | 状態 |
|------|------|
| **ストレージノード** | 「意味不明な断片」を持っているだけ。チェーンの目次と照合して解読する義理も機能もない |
| **法的な盾** | 「ストレージノードは中身を知らない」という防衛線を維持しつつ、ユーザー同士は自由に閲覧可能 |

### 13.3 DM（1対1）：ステルスアドレス + E2EE

特定の 1 人にだけ送る場合は、[memo.md](memo.md) に記載のステルスアドレス・プロトコルを使用。

```
送信者 ──[X25519鍵交換]──> 一時的な共有秘密
                              │
                              ▼
              ┌────────────────────────────┐
              │  ChaCha20-Poly1305 で暗号化 │
              │  ステルスアドレス宛に送信    │
              └────────────────────────────┘
```

#### 秘密鍵のペアダンス（詳細）

DMでも「相手が見れる」必要があるが、原理は同じ。

```
┌─────────────────────────────────────────────────────────────────┐
│                    DM 鍵交換プロセス                             │
│                                                                 │
│  1. 鍵の合成                                                     │
│     送信者: 自分の秘密鍵 × 相手の公開鍵 → 共有鍵 S               │
│                                                                 │
│  2. 暗号化                                                       │
│     メッセージを共有鍵 S で暗号化                                 │
│     → 暗号化後、鍵 S は捨てる（メモリから消去）                   │
│                                                                 │
│  3. 送信                                                         │
│     暗号文 + エフェメラル公開鍵をチェーンへ                       │
│     ※ 共有鍵 S 自体はネットワーク上に一度も流れない              │
│                                                                 │
│  4. 受信者の復号                                                  │
│     受信者: 自分の秘密鍵 × 送信者の公開鍵 → 共有鍵 S（再現）      │
│     → 全く同じ鍵を手元で生成し、復号                             │
└─────────────────────────────────────────────────────────────────┘
```

**重要**: ネットワーク上には一度も「解読できる状態の鍵」は流れない。秘密鍵という「マスターキー」を本人が持っているからこそできる。

### 13.3.1 「自分だけ」の場合：ローカル鍵の絶対王政

下書きや自分専用のメモなら、話は一番シンプル。

```
┌─────────────────────────────────────────────────────────────────┐
│                  「自分だけ」の暗号化                             │
│                                                                 │
│  1. 鍵の生成                                                     │
│     シードフレーズ（秘密鍵）から投稿専用の AES 鍵を派生           │
│     HKDF(秘密鍵, "post-" + PostId) → Key_Private                 │
│                                                                 │
│  2. 暗号化                                                       │
│     投稿内容を Key_Private で暗号化                               │
│     暗号文を SSS で断片化 → ストレージノードへ                    │
│                                                                 │
│  3. メタデータ                                                    │
│     チェーンには鍵のヒントすら流さない                            │
│     DecryptionKey: null                                         │
│                                                                 │
│  4. 復号                                                         │
│     将来、自分のデバイスで再度                                    │
│     HKDF(秘密鍵, "post-" + PostId) → Key_Private を再現          │
│     断片を収集 → 復号                                            │
└─────────────────────────────────────────────────────────────────┘
```

**セキュリティレベル:**

> 警察が全ストレージノードを物理的に押収して、スーパーコンピュータで 1 億年計算しても、あなたの脳内（またはデバイス内の IndexedDB）にある秘密鍵がない限り、中身は 1 bit も漏れない。宇宙の終わりまで安全。

### 13.4 鍵配布の比較表

| 公開範囲 | 鍵の扱い | 誰が復号できるか |
|---------|---------|----------------|
| **公開** | AES鍵をチェーンに平文で記載 | 誰でも |
| **フォロワー限定** | AES鍵をフォロワーの公開鍵で暗号化 | フォロワーの秘密鍵保持者のみ |
| **DM** | 一時的な共有秘密で暗号化 | 送信者と受信者のみ |
| **自分だけ** | AES鍵をローカルにのみ保存 | 投稿者本人のみ |

### 13.5 管理者（ノード運営者）が中身を見れない理由

ストレージノード運営者が中身を見れないのは、彼らが **「鍵を拾いに行って、組み立てて、解読する」という能動的な行為** をシステム的に禁止（あるいは機能として排除）されているから。

```
ストレージノードの視点:

┌───────────────────────────────────────────┐
│  保持しているもの                          │
│  ├── 断片 #1 (意味不明なバイト列)          │
│  ├── 断片 #2 (意味不明なバイト列)          │
│  └── 断片 #3 (意味不明なバイト列)          │
│                                           │
│  持っていないもの                          │
│  ├── 他の断片 (k-of-n で不足)              │
│  ├── 復号鍵 (チェーン上にあるが参照しない) │
│  └── 復元ロジック (実装されていない)        │
└───────────────────────────────────────────┘

結論: 「見ようと思えば見れる」が「見る機能がない」
```

#### 13.5.1 フルストレージノード問題（重要な例外）

> **「全断片を持っているノードがいたら、筒抜けやん」**

これは正しい指摘。**フルストレージノード**（全ての断片を保持するノード）は理論上、全ての公開投稿を復元・復号可能。

```
フルストレージノードの視点:

┌───────────────────────────────────────────┐
│  保持しているもの                          │
│  ├── 断片 #1 ✓                            │
│  ├── 断片 #2 ✓                            │
│  ├── 断片 #3 ✓                            │
│  ├── 断片 #4 ✓                            │
│  └── 断片 #5 ✓  ← k個以上揃っている！      │
│                                           │
│  チェーンから取得可能                       │
│  ├── 復号鍵 (公開投稿の場合)               │
│  └── 断片の対応関係                        │
└───────────────────────────────────────────┘

結論: 「見ようと思えば見れる」し「見る能力もある」
       → 公開投稿は筒抜け
```

**リスク評価:**

| 投稿タイプ | フルノードへのリスク |
|-----------|-------------------|
| **公開投稿** | **高**: 鍵も公開されているため完全に復元可能 |
| **フォロワー限定** | **低**: 復号鍵がフォロワーの公開鍵で暗号化されているため、フルノードでも復号不可 |
| **DM** | **なし**: ステルスアドレス + E2EE により完全に保護 |

**対策案:**

1. **断片配布の分散強制**
   - 同一オペレーターへの断片集中を禁止
   - 断片配布先をランダム化（地理的・論理的に分散）
   
   ```rust
   // 断片配布時のバリデーション
   fn validate_distribution(shards: &[ShardLocation]) -> Result<(), Error> {
       let unique_operators = shards.iter()
           .map(|s| s.operator_id)
           .collect::<HashSet<_>>();
       
       // 最低でも k 個以上の異なるオペレーターに分散
       ensure!(unique_operators.len() >= threshold, Error::InsufficientDistribution);
       Ok(())
   }
   ```

2. **経済的ディスインセンティブ**
   - 全断片保持は膨大なストレージコストがかかる
   - 報酬は「保持している断片数」に比例するので、全部持つメリットが薄い
   
   ```
   コスト:  全断片保持 = O(全投稿数 × 断片サイズ)
   報酬:    断片あたりの報酬 × 保持断片数
   
   → 全部持っても報酬は増えるが、コストも比例して増える
   → 「覗き見」のためだけに赤字を垂れ流す動機は低い
   ```

3. **運用的な現実**
   - ネットワーク規模が大きくなると、全断片保持は物理的に困難
   - Filecoin や IPFS でも同様の問題は存在するが、規模で緩和
   
   ```
   投稿数: 100万件
   断片数: 5断片/投稿
   断片サイズ: 1KB
   
   全断片保持 = 100万 × 5 × 1KB = 5GB（まだ現実的）
   
   投稿数: 10億件（Twitter規模）
   全断片保持 = 5TB（個人には厳しい）
   ```

**結論:**

> **「完璧な防御は存在しない。公開投稿はフルノードに見られる可能性がある。本当に隠したいならフォロワー限定か DM を使え。」**

これは「公開」の意味を正しく理解した上での設計。公開投稿は「誰でも見れる」のが仕様であり、フルノードに見られても問題ないデータのみを公開すべき。

## 14. 秘密鍵の保管と復旧

> **「秘密鍵は、君の魂の印鑑。それをブラウザの外に出さない限り、Anarchy の世界では君の秘密は絶対不可侵の領域に守られる。」**

### 14.1 なぜノード運営者は「鍵」すら見つけられないか

非公開投稿の場合、フルストレージノード保持者でも以下の絶望を味わう：

```
┌─────────────────────────────────────────────────────────────────┐
│               フルノード運営者の絶望                              │
│                                                                 │
│  1. 地図はあるが宝箱が透明                                        │
│     → チェーンを見ても「鍵」の欄が空っぽ（または無意味なハッシュ） │
│                                                                 │
│  2. 宝箱を拾っても開かない                                        │
│     → 運良く断片を集めて箱を組み立てても、                        │
│       鍵穴が「暗号学的なブラックホール」                          │
│                                                                 │
│  3. 誰の宝箱かも不明                                              │
│     → ステルスアドレスを使っていれば、                            │
│       それが誰宛ての箱なのかすら判別不可能                        │
└─────────────────────────────────────────────────────────────────┘
```

**結論**: 管理者がどうこうできる余地を「数学」で物理的に消し飛ばしている。

### 14.2 秘密鍵のブラウザ内保管

秘密鍵をブラウザ内でどう安全に保管するか。

#### オプション A: 暗号化 Keystore ファイル

```typescript
// キーストアの構造
interface EncryptedKeystore {
  version: 1;
  crypto: {
    cipher: 'chacha20-poly1305';
    ciphertext: string;      // 暗号化されたシードフレーズ
    nonce: string;
    kdf: 'argon2id';
    kdfparams: {
      memory: 65536;         // 64MB
      iterations: 3;
      parallelism: 4;
      salt: string;
    };
  };
  address: string;           // AccountId（検証用）
}
```

**フロー:**
```
パスワード入力
    │
    ▼ Argon2id (メモリハード KDF)
派生鍵
    │
    ▼ ChaCha20-Poly1305
シードフレーズを暗号化
    │
    ▼ IndexedDB に保存
```

**メリット:**
- パスワードなしでは秘密鍵を取り出せない
- メモリハード KDF でブルートフォース耐性

**リスク:**
- 悪意あるフロントエンドがパスワード入力時に盗聴可能
- → ブラウザ拡張ウォレット連携で緩和（TODO.md 参照）

#### オプション B: ブラウザ拡張ウォレット連携

```
┌─────────────────┐     ┌─────────────────┐
│   フロントエンド  │     │  Talisman 等    │
│   (Next.js)     │ ──→ │  拡張ウォレット   │
│                 │     │                 │
│  署名リクエスト   │     │  秘密鍵は       │
│  のみ送信        │     │  ここで管理      │
└─────────────────┘     └─────────────────┘
```

**メリット:**
- フロントエンドは秘密鍵に一切触れない
- ハイドラ戦略との相性抜群（どのフロントを使っても安全）

**実装**: PAPIの `@polkadot-api/pjs-signer` で連携可能

### 14.3 ソーシャル・リカバリー（構想）

> **「秘密鍵を紛失した時に、フォロワーの助けを借りてアカウントを復旧する」**

秘密鍵を紛失した場合、通常は全てのデータにアクセス不能になる。ソーシャル・リカバリーはこれを緩和する仕組み。

#### 仕組み

```
┌─────────────────────────────────────────────────────────────────┐
│                  ソーシャル・リカバリー設定時                      │
│                                                                 │
│  1. リカバリー用の秘密 R を生成                                    │
│                                                                 │
│  2. R を SSS で分割（例: 5人中3人で復元可能）                       │
│     ┌───┬───┬───┬───┬───┐                                       │
│     │ S1│ S2│ S3│ S4│ S5│                                       │
│     └───┴───┴───┴───┴───┘                                       │
│       │   │   │   │   │                                         │
│       ▼   ▼   ▼   ▼   ▼                                         │
│     友人A 友人B 友人C 友人D 友人E                                  │
│     (それぞれの公開鍵で暗号化して配布)                              │
│                                                                 │
│  3. R で暗号化された「アカウント移行用の情報」をチェーンに保存       │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                  リカバリー実行時                                 │
│                                                                 │
│  1. 新しいデバイスで新しい鍵ペアを生成                             │
│                                                                 │
│  2. 友人 3人以上に連絡し、断片を送ってもらう                       │
│     (友人は自分の秘密鍵で復号して断片を渡す)                        │
│                                                                 │
│  3. 断片を結合して R を復元                                        │
│                                                                 │
│  4. R で「アカウント移行用の情報」を復号                           │
│                                                                 │
│  5. 新しい鍵ペアでアカウントを再構築                               │
└─────────────────────────────────────────────────────────────────┘
```

#### 制限事項

| 復旧可能 | 復旧不可能 |
|---------|-----------|
| Identity（アカウント自体） | 「自分だけ」の投稿（鍵が失われているため） |
| フォロワー関係 | 過去のDM履歴 |
| 公開投稿へのアクセス | 秘密鍵で派生した全ての暗号化データ |

**注意**: ソーシャル・リカバリーは「アカウントの継続性」を保証するが、「過去の非公開データ」は原理的に復旧不可能。これは機能ではなく、暗号学的な限界。

#### 設計上の懸念

- **共謀リスク**: 友人が結託して不正に復旧を試みる可能性
  - → 緩和策: タイムロック（リカバリー要求後 7日間の待機期間）
  - → 緩和策: 本人への通知（元の鍵でキャンセル可能）
  
- **友人の鍵紛失**: 友人が自分の秘密鍵を紛失したら断片が取り出せない
  - → 緩和策: 十分な冗長性（5人中3人など）
