## Clarifications

## 概要

Anarchyフロントエンドに4つの主要機能を追加し、ユーザー体験を向上させる:

1. **送金フォーム**: ユーザー間でMORALトークンを直接送金（常時表示）
2. **メディア添付対応**: 投稿に画像・動画を添付（既存分散ストレージ基盤を活用）
3. **投稿者名表示**: AccountIdの見やすい表示とコピー機能
4. **ニックネーム登録**: 自分のAccountIdに表示名を設定（Nickname Pallet）

## User Scenarios & Testing

### User Story 1 - MORAL送金 (Priority: P1)

ユーザーAは、ユーザーBにMORALトークンを送金したい。MORAL残高表示の下にある送金フォームに宛先AccountIdと金額を入力し、確認ダイアログで内容を確認してから送金を実行する。

**Why this priority**: 送金はトークン経済の基本機能であり、ユーザー間の価値移転を可能にする最も重要な機能。

**Independent Test**: 送金フォームに有効なAccountIdと金額を入力し、確認ダイアログで送金を実行。トランザクション成功後、送信者と受信者の残高変化を確認。

**Acceptance Scenarios**:

1. **Given** ユーザーが100 MORAL以上の残高を持っている, **When** 有効なAccountIdと50 MORALを入力して送金ボタンを押す, **Then** 確認ダイアログが表示され、宛先と金額が確認できる
2. **Given** 確認ダイアログが表示されている, **When** 「送金する」を押す, **Then** トランザクションが成功し、残高が更新される
3. **Given** 確認ダイアログが表示されている, **When** 「キャンセル」を押す, **Then** ダイアログが閉じ、送金は実行されない
4. **Given** ユーザーの残高が10 MORAL, **When** 50 MORALの送金を試みる, **Then** 「残高不足」エラーが表示され、送金は実行されない
5. **Given** 送金フォームに入力中, **When** 無効なAccountId形式を入力, **Then** 「無効なアドレス」エラーが表示される
6. **Given** 送金が進行中, **When** ネットワークエラーが発生, **Then** ユーザーに適切なエラーメッセージが表示される

---

### User Story 2 - 投稿者名表示とコピー (Priority: P2)

ユーザーはタイムラインで投稿を閲覧する際、投稿者のAccountIdを見やすい短縮形式で確認したい。また、AccountIdをクリックしてクリップボードにコピーしたい。

**Why this priority**: UX改善として重要。低コストで実装可能であり、他ユーザーへの送金や報告に必要なAccountId取得を容易にする。

**Independent Test**: タイムラインで投稿を表示し、投稿者のAccountIdが短縮形式（先頭6文字...末尾4文字）で表示されることを確認。クリックでフルAccountIdがコピーされる。

**Acceptance Scenarios**:

1. **Given** タイムラインに投稿が表示されている, **When** 投稿者名エリアを表示, **Then** AccountIdが「5GrwvaEF...vYR」形式で短縮表示される
2. **Given** 投稿者のAccountIdが表示されている, **When** AccountIdをクリック, **Then** フルAccountIdがクリップボードにコピーされ、「Copied!」確認が表示される
3. **Given** 投稿者のAccountIdが表示されている, **When** AccountIdにマウスホバー, **Then** ツールチップでフルAccountIdが表示される

---

### User Story 3 - 画像添付投稿 (Priority: P3)

ユーザーは投稿に画像を添付したい。投稿フォームで画像を選択またはドラッグ&ドロップし、プレビューを確認してから投稿する。最大4ファイルまで添付可能。

**Why this priority**: SNSの基本機能として重要だが、既存のテキスト投稿機能が動作していることが前提。

**Independent Test**: 投稿フォームで画像ファイルを選択し、プレビュー表示を確認。投稿後、タイムラインで画像が固定最大幅・アスペクト比維持で表示される。

**Acceptance Scenarios**:

1. **Given** 投稿フォームが表示されている, **When** JPEG画像（10MB）をドラッグ&ドロップ, **Then** 画像プレビューとアップロード進捗（%）が表示される
2. **Given** 画像がプレビュー表示されている, **When** 投稿ボタンをクリック, **Then** 画像が分散ストレージに保存され、投稿が作成される
3. **Given** タイムラインに画像付き投稿がある, **When** 投稿を表示, **Then** 画像が固定最大幅でアスペクト比維持表示される
4. **Given** タイムラインの画像を表示中, **When** 画像をクリック, **Then** フルサイズで画像が表示される
5. **Given** 投稿フォームに3枚の画像が添付されている, **When** 4枚目の画像を追加, **Then** 4枚目も正常に追加される
6. **Given** 投稿フォームに4枚の画像が添付されている, **When** 5枚目の画像を追加, **Then** 「最大4ファイルまで」エラーが表示される
7. **Given** 投稿フォームが表示されている, **When** 150MB画像を選択, **Then** 「ファイルサイズ上限超過」エラーが表示される
8. **Given** 投稿フォームが表示されている, **When** PDFファイルを選択, **Then** 「対応していないフォーマット」エラーが表示される

---

### User Story 4 - 動画添付投稿 (Priority: P4)

ユーザーは投稿に動画を添付したい。

**Why this priority**: 画像添付と同じ基盤を使用するが、ファイルサイズが大きいためP4。

**Independent Test**: 投稿フォームで動画ファイルを選択し、サムネイル表示を確認。投稿後、タイムラインで動画再生が可能。

**Acceptance Scenarios**:

1. **Given** 投稿フォームが表示されている, **When** MP4動画（100MB）を選択, **Then** 動画サムネイルプレビューが表示される
2. **Given** 動画付き投稿がタイムラインにある, **When** 投稿を表示, **Then** 動画プレイヤーが表示され、再生可能
3. **Given** 投稿フォームが表示されている, **When** 1.5GB動画を選択, **Then** 「ファイルサイズ上限超過」エラーが表示される
4. **Given** 投稿フォームが表示されている, **When** AVI形式を選択, **Then** 「対応していないフォーマット」エラーが表示される

---

### User Story 5 - ニックネーム登録 (Priority: P2)

ユーザーは自分のAccountIdに表示名（ニックネーム）を設定したい。設定したニックネームは他のユーザーにも表示され、いつでも変更可能。

**Why this priority**: ユーザー識別のUX向上に直結。送金時の確認やタイムラインでの投稿者識別が容易になる。

**Independent Test**: 設定画面でニックネームを入力して保存。タイムラインで自分の投稿にニックネームが表示されることを確認。

**Acceptance Scenarios**:

1. **Given** ユーザーがログイン済み, **When** ニックネーム設定画面を開く, **Then** 現在のニックネーム（未設定なら空欄）が表示される
2. **Given** ニックネーム入力欄がある, **When** "alice_anarchy"と入力して保存, **Then** トランザクションが成功し、ニックネームがオンチェーンに保存される
3. **Given** ニックネームが設定済み, **When** タイムラインで自分の投稿を表示, **Then** AccountIdの代わりにニックネームが表示される
4. **Given** ニックネームが設定済み, **When** 別のニックネームに変更, **Then** 新しいニックネームで上書きされる
5. **Given** ニックネームが設定済み, **When** ニックネームを削除, **Then** AccountId短縮表示に戻る
6. **Given** 他ユーザーがニックネームを設定済み, **When** そのユーザーの投稿を表示, **Then** ニックネーム + AccountId短縮の両方が表示される
7. **Given** ニックネーム入力欄がある, **When** 33文字以上を入力, **Then** 「ニックネームは32文字以内」エラーが表示される

---

### Edge Cases

- 送金中にブラウザを閉じた場合、トランザクションの状態はどうなるか？→ ブロックチェーンに送信済みなら処理される
- 超長文テキスト + 複数画像の投稿時、アップロード順序と失敗時のロールバックはどうなるか？→ 全メディアアップロード成功後にオンチェーン投稿を実行
- クリップボードAPIが利用できないブラウザでのコピー機能は？→ フォールバックとして手動選択を促すメッセージ表示
- 画像/動画の復元に失敗した場合のタイムライン表示は？→ プレースホルダー画像とエラーメッセージを表示
- 同じニックネームを複数ユーザーが設定した場合は？→ ユニーク制約なし、識別はAccountIdで行うため許容

## Requirements

### Functional Requirements

**送金フォーム**
- **FR-001**: システムはMORAL残高表示の下に常時表示される送金フォームを提供しなければならない
- **FR-002**: システムはSS58形式のAccountIdを検証しなければならない
- **FR-003**: システムは送金額が残高を超えていないことを検証しなければならない
- **FR-004**: システムは `Balances.transfer_allow_death` を使用して送金を実行しなければならない
- **FR-005**: システムは送金の進行状況（pending/success/error）を表示しなければならない
- **FR-006**: システムは送金成功後に残高を自動更新しなければならない
- **FR-007**: システムはエラー時にユーザーフレンドリーなメッセージを表示しなければならない
- **FR-008**: システムは送金実行前に確認ダイアログを表示し、宛先と金額を再確認させなければならない

**投稿者名表示**
- **FR-009**: システムはAccountIdを短縮形式（先頭6文字...末尾4文字）で表示しなければならない
- **FR-010**: システムはAccountIdクリックでフルアドレスをクリップボードにコピーしなければならない
- **FR-011**: システムはコピー成功時に視覚的フィードバックを表示しなければならない
- **FR-012**: システムはホバー時にフルAccountIdをツールチップで表示しなければならない
- **FR-013**: システムはニックネーム設定済みユーザーの投稿でニックネームを優先表示しなければならない

**ニックネーム登録（Nickname Pallet）**
- **FR-014**: システムは軽量なNickname Palletを新規作成しなければならない
- **FR-015**: システムはニックネームの設定・変更・削除をサポートしなければならない
- **FR-016**: システムはニックネームを最大32文字（UTF-8で最大128バイト）に制限しなければならない
- **FR-017**: システムはニックネームのユニーク制約を設けない（重複許可、識別はAccountId）
- **FR-018**: システムはニックネーム設定UIを提供しなければならない
- **FR-019**: システムはニックネーム設定成功時に視覚的フィードバックを表示しなければならない

**メディア添付**
- **FR-020**: システムはドラッグ&ドロップとファイル選択による画像アップロードをサポートしなければならない
- **FR-021**: システムは画像プレビュー表示を提供しなければならない
- **FR-022**: システムは動画アップロードとサムネイルプレビューをサポートしなければならない
- **FR-023**: システムはファイルサイズ制限を適用しなければならない（画像: 100MB、動画: 1000MB）
- **FR-024**: システムは対応フォーマットを検証しなければならない（画像: JPEG/PNG/GIF/WebP、動画: MP4/WebM）
- **FR-025**: システムはメディアを既存分散ストレージ基盤で保存しなければならない
- **FR-026**: システムはタイムラインでメディアを固定最大幅・アスペクト比維持で表示しなければならない
- **FR-027**: システムはメディアクリックでフルサイズ表示を提供しなければならない
- **FR-028**: システムはメディア復元失敗時にプレースホルダーを表示しなければならない
- **FR-029**: システムは1投稿あたり最大4ファイルまでのメディア添付をサポートしなければならない
- **FR-030**: システムは画像・動画の混在添付をサポートしなければならない
- **FR-031**: システムはアップロード進捗をパーセンテージとプログレスバーで表示しなければならない

**共通**
- **FR-032**: 全テキストは国際化（i18n）対応しなければならない
- **FR-033**: システムは日本語・英語・中国語をサポートしなければならない

### Key Entities

- **TransferRequest**: 送金リクエスト（宛先AccountId、金額、送信者）
- **MediaFile**: アップロードされるメディアファイル（種別、サイズ、フォーマット、バイナリデータ）
- **MediaRef**: 投稿に紐づくメディア参照（Merkle Root、種別、サイズ、寸法）
- **AddressDisplay**: 表示用アドレス情報（AccountId、短縮形式、ニックネーム）
- **Nickname**: ユーザーの表示名（AccountId→ニックネームのマッピング、最大32文字、重複許可）

## Success Criteria

### Measurable Outcomes

- **SC-001**: ユーザーは送金操作を60秒以内に完了できる（モーダル表示から送金確認まで）
- **SC-002**: AccountIdコピー操作の成功率は95%以上
- **SC-003**: 10MB以下の画像アップロードは30秒以内に完了する
- **SC-004**: 100MB以下の動画アップロードは5分以内に完了する
- **SC-005**: メディア付き投稿の表示（復元）は10秒以内に開始される（大きなメディアは段階的読み込み）
- **SC-006**: バリデーションエラーは操作後1秒以内に表示される
- **SC-007**: モバイルブラウザでも全機能が利用可能（レスポンシブ対応）
- **SC-008**: ニックネーム設定は30秒以内に完了する
- **SC-009**: ニックネーム設定済みユーザーの表示名はタイムライン読み込み時に同時に取得される

## Scope & Constraints

### 実装範囲

- **フロントエンド変更**: メインスコープ
- **ブロックチェーン変更**: 必要に応じて許可（例: メディア添付のためのPost Pallet拡張）
- **ストレージノード変更**: 必要に応じて許可

### デザイン方針

- **UX重視**: 技術的な最適解よりもユーザー体験を優先する
- **直感的な操作**: 説明不要で使えるインターフェース
- **即座のフィードバック**: 全操作に対して視覚的な応答を提供
- **エラー回復の容易さ**: エラー時も次のアクションが明確
- **一貫性**: 既存UIパターンとの調和

## Assumptions

- 既存の分散ストレージ基盤（SSS分割、Storage Node）が正常に動作している
- PAPI（polkadot-api）経由でのブロックチェーン接続が確立されている
- ユーザーは署名用のAccountId（シードフレーズから導出）を持っている
- ブラウザはClipboard APIをサポートしている（フォールバック対応も実装）
- 大容量メディアアップロード時はWeb Workerで分割処理を行う
- ブロックチェーン側の変更が必要な場合、Post Palletの拡張（media_refs追加等）を行う
