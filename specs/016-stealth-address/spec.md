# Feature Specification: ステルスアドレス統合

**Feature Branch**: `016-stealth-address`  
**Created**: 2026-02-27  
**Status**: Implemented  
**Input**: ステルスアドレス統合機能：クライアント側暗号実装（X25519鍵交換、ワンタイムアドレス導出、スキャン鍵/閲覧鍵ペア生成、Wasm実装 + Web Worker）、Stealth Pallet作成（ステルスアドレス宛トランザクション、エフェメラル公開鍵格納）、クライアント側スキャナー（バックグラウンドスキャン処理、自分宛トランザクション検出、復号・残高更新）

## 概要

ステルスアドレスは、受取人のプライバシーを保護するための暗号技術です。送金ごとに一意のワンタイムアドレスを生成し、ブロックチェーン上で受取人の実際のアドレスを公開せずに資金を受け取ることを可能にします。これにより、第三者が特定のアドレスへの複数の支払いをリンクすることが不可能になります。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ステルスメタアドレス生成 (Priority: P1)

ユーザーとして、自分専用のステルスメタアドレス（スキャン鍵ペアと閲覧鍵ペア）を生成し、送金者に安全に共有できるようにしたい。

**Why this priority**: ステルスアドレスシステムの基盤となる機能。この鍵ペアがなければ、ステルス送金を受け取ることができない。

**Independent Test**: ユーザーがアプリ上でステルスメタアドレスを生成し、エクスポート可能な形式で取得できることを確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーがログイン済みの状態, **When** ステルスアドレス生成ボタンを押す, **Then** スキャン鍵ペアと閲覧鍵ペアが生成され、ステルスメタアドレスが表示される
2. **Given** ステルスメタアドレスが生成済み, **When** 共有ボタンを押す, **Then** 送金者に渡せる形式（QRコード等）でメタアドレスがエクスポートされる
3. **Given** ステルスメタアドレスが生成済み, **When** 秘密鍵のバックアップを選択, **Then** 暗号化されたバックアップファイルがダウンロードできる
4. **Given** 新しいセッション開始時, **When** ステルスアドレス機能を使用, **Then** バックアップファイルのインポートが要求される

---

### User Story 2 - ステルスアドレスへの送金 (Priority: P1)

送金者として、受取人のステルスメタアドレスを使って、第三者にリンク不可能なワンタイムアドレスに資金を送りたい。

**Why this priority**: ステルスアドレスの核心機能。実際の送金ができなければプライバシー保護の価値を提供できない。

**Independent Test**: 送金者がメタアドレスを入力し、ワンタイムアドレスへの送金トランザクションが正常にブロックチェーンに記録されることを確認する。

**Acceptance Scenarios**:

1. **Given** 送金者が受取人のステルスメタアドレスを持っている, **When** 金額を指定して送金を実行, **Then** ワンタイムアドレスが自動生成され、トランザクションがブロックチェーンに記録される
2. **Given** 送金トランザクションが実行された, **When** トランザクションが確定, **Then** エフェメラル公開鍵がチェーン上に公開され、受取人がスキャンできる状態になる
3. **Given** 無効なステルスメタアドレスが入力された, **When** 送金を試みる, **Then** エラーメッセージが表示され、送金が実行されない

---

### User Story 3 - ステルス送金の受取検出 (Priority: P1)

受取人として、自分宛のステルス送金をバックグラウンドで自動検出し、残高に反映させたい。

**Why this priority**: 受取人がステルス送金を実際に受け取るために必須の機能。これがなければ送金されても気づけない。

**Independent Test**: 受取人のアプリがバックグラウンドでスキャンを実行し、自分宛の送金を検出・残高更新できることを確認する。

**Acceptance Scenarios**:

1. **Given** 受取人がスキャナーを有効化している, **When** 新しいブロックでエフェメラル公開鍵が公開される, **Then** 自動的にスキャンが実行され、自分宛かどうか判定される
2. **Given** 自分宛のステルス送金が検出された, **When** ワンタイムアドレスの秘密鍵が導出される, **Then** 残高が更新され、通知が表示される
3. **Given** 他人宛のステルス送金がスキャンされた, **When** 復号を試みる, **Then** 自分宛ではないと判定され、スキップされる

---

### User Story 4 - ステルス残高の使用 (Priority: P2)

受取人として、ステルスアドレスで受け取った資金を、プライバシーを維持しながら使用したい。

**Why this priority**: 受け取った資金を実際に使えなければ意味がない。ただし、受取機能が先に完成している必要がある。

**Independent Test**: ステルスアドレスで受け取った残高から通常の送金ができることを確認する。

**Acceptance Scenarios**:

1. **Given** ステルスアドレスに残高がある, **When** 別のアドレスへ送金を実行, **Then** ワンタイムアドレスの秘密鍵で署名され、トランザクションが送信される
2. **Given** 複数のステルス受取がある, **When** 送金額が1つの残高を超える, **Then** 自動コインセレクションにより手数料最適化された複数UTXOが選択され、リンク性警告が表示される
3. **Given** 複数UTXOが選択された, **When** ユーザーが警告を確認して続行, **Then** 複数のワンタイムアドレスから資金が集約されて送金される

---

### User Story 5 - スキャナー設定管理 (Priority: P3)

ユーザーとして、スキャナーの動作設定（頻度、通知、バッテリー消費）を管理したい。

**Why this priority**: ユーザー体験向上のための追加機能。基本機能が動作してから最適化すべき。

**Independent Test**: スキャン頻度の変更が実際のスキャン動作に反映されることを確認する。

**Acceptance Scenarios**:

1. **Given** スキャナー設定画面, **When** スキャン頻度を変更, **Then** 新しい頻度でスキャンが実行される
2. **Given** バッテリー節約モードが有効, **When** アプリがバックグラウンドに移行, **Then** スキャン頻度が自動的に低下する

---

### Edge Cases

- スキャン鍵の復元時に、過去の未検出トランザクションはジェネシスブロックからフルスキャンで検出する（暫定決定：時間がかかるが確実）
- ネットワーク断時にスキャンが失敗した場合の再試行ロジック
- 大量のエフェメラル公開鍵がある場合のスキャンパフォーマンス
- ステルスメタアドレスのバックアップを紛失した場合のリカバリー
- Web Workerが利用できない古いブラウザでのフォールバック動作

## Requirements *(mandatory)*

### Functional Requirements

#### クライアント側暗号機能

- **FR-001**: システムは、X25519曲線を使用したスキャン鍵ペア（秘密鍵・公開鍵）を生成できなければならない
- **FR-002**: システムは、X25519曲線を使用した閲覧鍵ペア（秘密鍵・公開鍵）を生成できなければならない
- **FR-003**: システムは、スキャン公開鍵と閲覧公開鍵を組み合わせたステルスメタアドレスを生成できなければならない
- **FR-004**: 送金者は、受取人のステルスメタアドレスとエフェメラル秘密鍵から、ワンタイムアドレスを導出できなければならない
- **FR-005**: 受取人は、自分のスキャン秘密鍵とエフェメラル公開鍵から、自分宛かどうかを判定できなければならない
- **FR-006**: 受取人は、自分宛と判定されたワンタイムアドレスの秘密鍵を導出できなければならない
- **FR-007**: すべての暗号処理は、Web WorkerでWasmモジュールとして実行されなければならない
- **FR-008**: 暗号処理はメインスレッドをブロックしてはならない

#### Stealth Pallet（ブロックチェーン）

- **FR-009**: パレットは、ステルスアドレス宛のトランザクションを受け付けなければならない
- **FR-010**: パレットは、各ステルストランザクションのエフェメラル公開鍵をオンチェーンに記録しなければならない
- **FR-011**: パレットは、ワンタイムアドレスへの残高移転を正しく処理しなければならない
- **FR-012**: パレットは、ワンタイムアドレスからの送金（秘密鍵保持者による署名）を許可しなければならない
- **FR-013**: エフェメラル公開鍵は、ブロック番号と共にストレージに記録され、標準Substrate RPCで取得可能でなければならない（専用RPCは不要、将来的にインデクサーで効率化）

#### クライアント側スキャナー

- **FR-014**: スキャナーは、新しいブロックのエフェメラル公開鍵を自動的にスキャンしなければならない
- **FR-015**: スキャナーは、Web Worker内でバックグラウンド実行されなければならない
- **FR-016**: 自分宛のステルス送金が検出された場合、セッション状態として検出済みUTXO情報を保持し、残高を更新しなければならない（永続化はしない）
- **FR-017**: スキャナーは、アプリがフォアグラウンドに戻った際に、見逃したブロックをキャッチアップしなければならない
- **FR-018**: 検出された送金について、ユーザーに通知を表示しなければならない

#### セキュリティ要件

- **FR-019**: スキャン秘密鍵と閲覧秘密鍵は、ブラウザ外に送信されてはならない
- **FR-020**: 秘密鍵はブラウザストレージに永続化せず、セッション中のみメモリに保持しなければならない（セッション開始時にバックアップからインポート）
- **FR-021**: バックアップエクスポートは、ユーザー指定のパスワードで暗号化されなければならない
- **FR-022**: セッション終了時（タブを閉じる、ページ遷移等）にメモリ上の秘密鍵を確実に破棄しなければならない

### Key Entities

- **ステルスメタアドレス (Stealth Meta-Address)**: スキャン公開鍵と閲覧公開鍵を含む、受取人が公開できるアドレス情報。送金者はこれを使ってワンタイムアドレスを生成する
- **ワンタイムアドレス (One-Time Address)**: 各ステルス送金で生成される一意のアドレス。受取人のみが秘密鍵を導出可能
- **エフェメラル鍵ペア (Ephemeral Key Pair)**: 送金者が各送金ごとに生成する一時的な鍵ペア。公開鍵のみがオンチェーンに公開される
- **スキャン鍵ペア (Scan Key Pair)**: 受取人が保持し、自分宛の送金を検出するために使用する鍵ペア
- **閲覧鍵ペア (View Key Pair)**: 受取人が保持し、ワンタイムアドレスの秘密鍵を導出するために使用する鍵ペア
- **ステルストランザクション (Stealth Transaction)**: ワンタイムアドレスとエフェメラル公開鍵を含むオンチェーントランザクション

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーは30秒以内にステルスメタアドレスを生成できる
- **SC-002**: ステルス送金のトランザクション送信から確定まで、通常送金と同等の時間（6秒以内）で完了する
- **SC-003**: スキャナーは1ブロック（1,000件以下のエフェメラル公開鍵）を2秒以内にスキャン完了する
- **SC-004**: 自分宛送金の検出から残高更新まで5秒以内に完了する
- **SC-005**: 初回ユーザーの95%が、ガイダンスを見てステルス送金を正常に完了できる
- **SC-006**: 暗号処理によるメインスレッドのブロッキングは100ms未満に抑える
- **SC-007**: スキャナーのバックグラウンド動作で、バッテリー消費増加は10%未満に抑える

## Assumptions

- ユーザーの既存AccountIDとの統合は、ステルスアドレス専用の鍵管理として独立して実装する
- エフェメラル公開鍵のオンチェーンストレージは、ガベージコレクション対象外として永続化する（プライバシーのため）
- Web Workerが利用できないブラウザでは、メインスレッド実行にフォールバックする（パフォーマンス警告を表示）
- 初期実装ではシングルサイン送金のみサポートし、マルチシグへの対応は将来の拡張とする
- **プロトコル標準**: EIP-5564互換方式をSubstrate向けに適応して採用する（ワンタイムアドレス導出アルゴリズム、メタアドレスエンコード形式はEIP-5564に準拠）

## Clarifications

### Session 2026-02-27

- Q: ステルスアドレスのプロトコル標準は？ → A: EIP-5564互換（Ethereumステルスアドレス標準をSubstrate向けに適応）
- Q: ステルス残高の集約方法は？ → A: 自動コインセレクション（手数料最適化で複数UTXOを自動選択、リンク性はユーザーに警告）
- Q: フルスキャン時の開始ブロックは？ → A: ジェネシスブロックから全履歴スキャン（暫定：時間がかかるが確実）
- Q: エフェメラル公開鍵のクエリ方法は？ → A: 標準Substrate RPCでブロックをフェッチし、クライアント側でパース（将来的にインデクサー導入予定のためフロントへの負荷は許容、チェーン側は軽量に保つ）
- Q: 秘密鍵のストレージ方式は？ → A: ブラウザストレージには永続化しない（セッション中のみメモリ保持、毎回バックアップからインポート）
