# Feature Specification: 初回署名 + セッショントークンによるストレージノードアクセス制限

**Feature Branch**: `018-storage-node-auth`  
**Created**: 2026-03-01  
**Status**: Ready for Review  
**Input**: ストレージノードへのアクセスをブロックチェーンノードからのみに制限する。フロントエンドユーザーが直接ストレージノードにアクセスすることを防ぐ。

## 設計目標

本仕様は以下の3つの制約を同時に満たす:

| # | 制約 | 実現方法 |
|---|------|----------|
| 1 | **誰でもP2P接続できる** | libp2pオープン接続 + スコアシステムで悪意ノード排除 |
| 2 | **複数ブロックチェーンノードと通信できる** | P2P接続済みピアは動的にセッション取得可能、HashMap<Token, PeerId>で管理 |
| 3 | **ブロックチェーン・ストレージノード以外からはアクセス不可** | P2P接続済み = 信頼（フロントエンドはP2P接続しない）|

## 背景

現在のアーキテクチャでは、フロントエンドはブロックチェーンノード（9944）経由でストレージノード（3030）にアクセスする設計だが、ストレージノードのRPCはX-Anarchy-Auth認証を使用しており、有効なSr25519署名があれば誰でもアクセス可能。これはセキュリティ上の問題であり、設計原則「フロントエンドはブロックチェーンノード経由でのみストレージにアクセスする」に違反する可能性がある。

## 認証方式

**初回署名 + セッショントークン方式**を採用する。

```
┌──────────────────────┐          ┌─────────────────────┐
│  ブロックチェーンノードA │          │  ストレージノード     │
└──────────┬───────────┘          └─────────┬───────────┘
           │                                  │
           │ ① storage_requestSession         │
           │   (Ed25519署名付き)              │
           │─────────────────────────────────>│
           │                                  │ 署名検証 → トークンA生成
           │ ② token_a                        │ HashMap<Token, PeerId>に追加
           │<─────────────────────────────────│
           │                                  │
           │ ③ HTTP RPC + X-Session-Token     │
           │─────────────────────────────────>│
           │   (token_a)                      │ トークン照合（高速）
           │                                  │
```

### 設計原則

1. **オンチェーン登録不要**: ストレージノードはP2P接続済みのピアからのセッション要求を受け付ける（設定不要）
2. **初回のみ署名検証**: 計算コストの高いEd25519検証は初回接続時のみ
3. **以降はトークン認証**: 高速なトークン照合でリクエストを認証
4. **複数ノード対応**: 各ブロックチェーンノードが独自のトークンを取得、HashMap<Token, PeerId>で管理
5. **分散配置対応**: ブロックチェーンノードとストレージノードは別マシンに配置可能
6. **P2P接続 = 信頼**: libp2pで接続済みのピアは自動的に信頼される（フロントエンドはP2P接続しないため除外）
7. **ストレージノード間通信は例外**: ストレージノード同士の通信は認証対象外。リペア・フラグメント同期はlibp2p P2Pのみ、HTTPは`/health`エンドポイントのみ許可

### 認証対象の整理

| 通信パターン | 認証 | 理由 |
|-------------|------|------|
| フロントエンド → ストレージノード | **拒否** | 直接アクセス禁止 |
| ブロックチェーンノード → ストレージノード | **セッショントークン** | 信頼されたノードのみ |
| ストレージノード → ストレージノード (P2P libp2p) | **Noise** | libp2pのNoiseプロトコルでpeer_id検証済み |
| ストレージノード → ストレージノード (HTTP `/health`) | **不要** | ヘルスチェックのみ、データアクセスなし |

**補足**: libp2pのNoiseプロトコルは接続確立時にEd25519公開鍵を検証するため、peer_idの偽装は不可能。P2P接続はオープン（誰でも接続可能）だが、悪意あるノードはpallet-storageのスコアシステム（ScoreProvider）で管理・排除される。

### 信頼モデル（P2P接続ベース）

P2P接続済みのピアを信頼する動的モデルを採用：

```
┌─────────────────────────────────────────────────────────────┐
│                    ストレージノード                           │
│                                                              │
│  connected_peers: HashSet<PeerId>   ← libp2pが管理          │
│       ↓                                                      │
│  storage_requestSession(署名)                                │
│       ↓                                                      │
│  署名者のpeer_id ∈ connected_peers ?                        │
│       ↓ YES              ↓ NO                               │
│  トークン発行         403 Forbidden                         │
└─────────────────────────────────────────────────────────────┘
```

**動作**:
1. ブロックチェーンノードがlibp2pでストレージノードに接続
2. 接続確立時、`connected_peers`にpeer_idが追加される
3. `storage_requestSession`時、署名者のpeer_idが`connected_peers`に含まれるか検証
4. 含まれていればセッショントークンを発行

**メリット**:
- 設定不要（新規ノードは接続するだけでセッション取得可能）
- 動的追加・削除（接続/切断で自動管理）
- フロントエンドはP2P接続しないため自動的に除外
- libp2pのpeer_id = Ed25519公開鍵なので署名検証と一貫性あり

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ブロックチェーンノードがセッションを確立 (Priority: P1)

ブロックチェーンノードの運用者として、起動時にストレージノードとのセッションを確立したい。署名検証は初回のみで、以降はトークンで高速に認証される。

**Why this priority**: コア機能。セッション確立なしではストレージノードにアクセスできない。

**Independent Test**: ブロックチェーンノードを起動し、`storage_requestSession`でセッショントークンを取得できることを確認。

**Acceptance Scenarios**:

1. **Given** ブロックチェーンノードがlibp2pでストレージノードに接続済み, **When** Ed25519署名付きで`storage_requestSession`を呼び出す, **Then** セッショントークンが返され、ストレージノードのHashMapに登録される
2. **Given** 署名が不正または peer_idがconnected_peersに含まれない, **When** `storage_requestSession`を呼び出す, **Then** 403エラーが返される

---

### User Story 2 - セッショントークンでフラグメント転送 (Priority: P1)

ブロックチェーンノードの運用者として、取得したセッショントークンを使ってフラグメントを高速に転送したい。

**Why this priority**: コア機能。毎リクエストで署名検証すると性能が劣化する。

**Independent Test**: セッショントークン付きで`storage_storeFragment`を呼び出し、成功することを確認。

**Acceptance Scenarios**:

1. **Given** 有効なセッショントークンを保持, **When** `X-Session-Token`ヘッダー付きで`storage_storeFragment`を呼び出す, **Then** リクエストが受け付けられフラグメントが保存される
2. **Given** 無効なセッショントークン, **When** `storage_storeFragment`を呼び出す, **Then** 401エラーが返される

---

### User Story 3 - フロントエンドからの直接アクセスを拒否 (Priority: P1)

セキュリティ担当者として、フロントエンドユーザーがストレージノードに直接アクセスすることを防ぎたい。

**Why this priority**: セキュリティ要件。直接アクセスを許すとスパム攻撃が可能になる。

**Independent Test**: フロントエンドユーザーの鍵で`storage_requestSession`を呼び出し、拒否されることを確認。

**Acceptance Scenarios**:

1. **Given** フロントエンドユーザー（P2P接続していない）, **When** 署名付きで`storage_requestSession`を呼び出す, **Then** 403エラーが返される（connected_peersに含まれないため）
2. **Given** フロントエンドユーザーがセッショントークンなしでアクセス, **When** `storage_storeFragment`を呼び出す, **Then** 401エラーが返される

---

### User Story 4 - 複数ブロックチェーンノードの同時接続 (Priority: P2)

ストレージノードの運用者として、複数のブロックチェーンノードからの接続を同時に受け付けたい。

**Why this priority**: スケーラビリティ。本番環境では複数ノードが接続する。

**Independent Test**: 2つのブロックチェーンノードがそれぞれセッションを確立し、両方からのリクエストが成功することを確認。

**Acceptance Scenarios**:

1. **Given** ブロックチェーンノードAがセッション確立済み, **When** ブロックチェーンノードBが`storage_requestSession`を呼び出す, **Then** 両方のトークンがHashMapに存在し、両方からのリクエストが成功する

---

### User Story 5 - ストレージノード間通信は認証不要 (Priority: P1)

ストレージノードの運用者として、他のストレージノードとのリペア・同期通信は認証なしで行いたい。

**Why this priority**: リペア機能がブロックされると、データ冗長性が維持できない。

**Independent Test**: ストレージノードAからストレージノードBへのP2Pリペアリクエストが成功することを確認。

**Acceptance Scenarios**:

1. **Given** ストレージノードAとBが同じbootstrap_peersを共有, **When** Aが Bにリペアリクエストをlibp2pで送信, **Then** 認証なしでリクエストが成功する
2. **Given** ストレージノードAがBの`/health`エンドポイントを呼び出す, **When** ヘルスチェック, **Then** 認証なしで成功（ステータスのみ返す）

---

### Edge Cases

- **セッショントークンの有効期限**: デフォルト24時間。残り1時間で自動更新（ブロックチェーンノードが自動的に新トークンを取得）
- **ストレージノード再起動**: HashMapがクリアされるため、全ブロックチェーンノードが再接続必要
- **ブロックチェーンノード切断検知**: 一定時間（1時間）リクエストがないトークンは自動削除
- **同一ノードの再接続**: 同じpeer_idからの再セッション要求は新トークンを発行し、古いトークンを無効化
- **ストレージノード間HTTP通信の制限**: ストレージノード間のHTTP通信は`/health`エンドポイントのみ。リペア・フラグメント転送は全てlibp2p P2Pで行う（HTTP RPCは使用しない）
- **接続切断時の動作**: P2P接続が切断されるとconnected_peersから削除される。既存セッショントークンは有効期限まで維持（再接続不要）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ストレージノードは`storage_requestSession` RPCを提供し、Ed25519署名を検証してセッショントークンを発行しなければならない
- **FR-002**: `storage_requestSession`は、署名者のpeer_idがlibp2pの`connected_peers`に含まれる場合のみセッショントークンを発行しなければならない
- **FR-003**: セッショントークンはランダムな256ビット値で、HashMap<Token, PeerId>に保存しなければならない
- **FR-004**: 書き込み操作（`storage_storeFragment`、`storage_storeKzgShard`）は`X-Session-Token`ヘッダーを必須とし、トークンを照合しなければならない
- **FR-005**: 読み取り操作（`storage_getFragment`）は認証不要のまま維持する
- **FR-006**: セッショントークンは24時間で期限切れとなり、期限切れトークンでのリクエストは401を返さなければならない
- **FR-007**: ブロックチェーンノードは起動時に`storage_requestSession`を呼び出し、トークンをメモリに保持しなければならない。トークンの残り有効期限が1時間未満になったら自動的に新トークンを取得しなければならない
- **FR-008**: ストレージノード間通信は認証対象外とする。リペア・フラグメント同期はlibp2p P2Pのみ使用し、HTTPは`/health`エンドポイントのみ許可（他のHTTP RPCはストレージノード間で使用禁止）
- **FR-009**: ストレージノードの`/health`以外のHTTP RPCエンドポイントは、有効なセッショントークンまたはP2P接続なしではアクセスできないようにしなければならない

### Key Entities

- **SessionToken**: 256ビットランダム値。ブロックチェーンノードを識別するための一時的なトークン
- **SessionRegistry**: ストレージノードが保持するHashMap<Token, SessionInfo>。SessionInfoはpeer_id、発行時刻、最終アクセス時刻を含む
- **ConnectedPeers**: libp2pが管理する接続済みpeer_idのHashSet。セッション発行可否の判定に使用

### Observability

- **セッションログ**: セッション発行・失効時に基本情報をログ出力（peer_id、発行時刻、有効期限）。デバッグ・監査目的で使用

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: フロントエンドユーザーがストレージノードに直接アクセスした場合、100%拒否される
- **SC-002**: セッション確立後のフラグメント転送レイテンシは、現在の署名検証方式と比較して50%以上改善される
- **SC-003**: 10台のブロックチェーンノードが同時にセッションを維持でき、全ノードからのリクエストが成功する
- **SC-004**: セッショントークンの発行から24時間後に自動的に無効化される
- **SC-005**: ストレージノード間のリペア通信（libp2p）とヘルスチェック（HTTP `/health`）は認証なしで成功する
- **SC-006**: ストレージノード間のフラグメント転送・リペアは100% libp2p P2Pで実行され、HTTP RPCは使用されない

## Clarifications

### Session 2026-03-01

- Q: `storage_requestSession`へのDoS攻撃対策としてレート制限は必要か？ → A: libp2pのconnection limitで十分（追加実装不要）
- Q: セッショントークン発行時にログ出力やメトリクス記録は必要か？ → A: 基本ログのみ（peer_id、発行時刻、有効期限）
- Q: ブロックチェーンノードがストレージノードを発見する方法は？ → A: 既存のGossipsub/bootstrap_peersで発見（変更不要）
- Q: セッショントークンの期限切れが近づいた時、自動更新すべきか？ → A: 自動更新（残り1時間で自動的に新トークン取得）
- Q: セッショントークンがブロックチェーンノードから漏洩した場合の対策は？ → A: 現状維持（トークン漏洩はブロックチェーンノード侵害と同義、対象外）

## Assumptions

- ブロックチェーンノードは信頼できるエンティティとして扱う（悪意あるブロックチェーンノードは対象外）
- ブロックチェーンノードはlibp2p peer_id（Ed25519鍵）を持ち、ストレージノードにP2P接続する
- ストレージノード同士はlibp2pで相互に接続し、通信可能
- **DoS対策**: `storage_requestSession`への過剰リクエストはlibp2pのconnection limitで制御。P2P接続済みピアのみがセッションリクエスト可能なため、追加のレート制限は不要
- **トークン漏洩**: セッショントークンの漏洩はブロックチェーンノード自体の侵害と同義。ノード侵害時は他のセキュリティリスク（秘密鍵漏洩等）がより深刻なため、トークン単体の保護は対象外

## Dependencies

- ストレージノード（storage-node/）：`storage_requestSession` RPC追加、セッションレジストリ実装
- ストレージノード（storage-node/）：HTTP repair/recoveryコード削除
  - `src/rpc/client.rs`の`request_fragment_from_peer()`等HTTPベースのフラグメント取得を削除
  - `src/sync/repair.rs`等のHTTP経由リカバリロジックを削除
  - 全てlibp2p P2P（`request_fragment()`）に統一
- ブロックチェーンノード（node/）：起動時のセッション確立処理追加
- 既存のauth.rs：初回署名検証ロジックを流用
