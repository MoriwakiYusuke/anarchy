# Feature Specification: KZG-VSS 保持証明・報酬システム

**Feature Branch**: `011-kzg-proof-rewards`  
**Created**: 2026-02-15  
**Status**: Draft  
**Input**: User description: "KZG-VSSベースの保持証明・報酬システム。sharksをarkworksに置換し、BLS12-381上のVSSで断片化と検証を統合。保持証明成功時の$moral報酬分配（データサイズ依存）、スコア閾値による自然な忘却メカニズムを実装。"

## 概要

現在のSSS実装（sharks crate, GF(256)）をKZGベースの検証可能秘密分散（VSS）に置換し、ストレージノードが断片を正しく保持していることを暗号学的に証明可能にする。証明成功時に$moralを報酬として分配し、スコアが閾値を下回ったデータは報酬が0になり「自然に忘却」される経済的メカニズムを実現する。

**技術的基盤**:
- **BLS12-381曲線**: Ethereum EIP-4844と同一
- **Ethereum KZG Ceremony**: Trusted Setupを流用（数万人参加の儀式）
- **arkworks**: Rust暗号ライブラリスタック

**設計原則**:
- 同一の多項式がSSS（秘密分散）とKZG（コミットメント）の両方の役割を果たす
- シェア + 48バイトの証明で「正しいシェアを持っている」ことを検証可能
- **報酬プール**: 投稿費用の90%が報酬プールに蓄積され、ストレージノードへの報酬に使用
- スコアが閾値以上 → データサイズに応じた報酬。閾値未満 → 報酬0 → 経済的忘却

## Clarifications

### Session 2026-02-16

- Q: VSSのk-of-n閾値パラメータは？ → A: k=3, n=5（3-of-5構成）
- Q: 報酬計算のバッチ処理間隔は？ → A: 24時間ごと
- Q: ガベージコレクション猶予期間は？ → A: 7日間（デフォルト）
- Q: チャレンジ未応答の警告閾値は？ → A: 3回連続で警告
- Q: チャレンジ応答の猶予期間は？ → A: 600ブロック（約100分）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 投稿の暗号学的断片化 (Priority: P1)

投稿者がコンテンツを投稿すると、クライアント側でKZG-VSSにより3-of-5閾値で断片化される。各断片は検証可能な形式で生成され、KZGコミットメントがオンチェーンに記録される。

**Why this priority**: 全ての後続機能（保持証明、報酬分配）の基盤となるコア機能。これがなければ検証可能な分散ストレージは実現できない。

**Independent Test**: テスト投稿を作成し、KZGコミットメントがオンチェーンに保存され、3個以上のシェアから元データが復元できることを確認。

**Acceptance Scenarios**:

1. **Given** 投稿者が新規投稿を作成する, **When** Submit ボタンを押す, **Then** クライアント側でKZG-VSS分割が実行され、5個のシェアが生成される
2. **Given** KZG-VSSシェアが生成された, **When** ストレージノードへアップロードが完了する, **Then** KZGコミットメント（48バイト）がオンチェーンに記録される
3. **Given** 投稿費用が支払われる, **When** トランザクションが確定する, **Then** 投稿費用の90%が報酬プールに蓄積され、10%がバーンされる
4. **Given** 3個以上のシェアが取得可能である, **When** 閲覧者が投稿を表示する, **Then** Lagrange補間により元データが復元され表示される
5. **Given** 2個のシェアしか取得できない, **When** 復元を試みる, **Then** 復元に失敗しエラーメッセージが表示される

---

### User Story 2 - 保持証明の提出と検証 (Priority: P1)

ストレージノードが自身の保持するシェアの正当性を暗号学的に証明する。チェーンからのチャレンジに対し、シェアの値とKZG opening proofを提出し、オンチェーンで検証される。

**Why this priority**: 報酬分配の前提条件。証明なしに報酬を分配すると、データを持っていないノードにも報酬が渡ってしまう。

**Independent Test**: ストレージノードを起動し、チェーンからのチャレンジに対して有効な証明を提出し、検証が成功することを確認。

**Acceptance Scenarios**:

1. **Given** ストレージノードがシェアを保持している, **When** チェーンから「シェア[i]を証明せよ」というチャレンジが発行される, **Then** ノードはシェア値（32バイト）+ KZG proof（48バイト）を提出する
2. **Given** 有効な証明が提出された, **When** オンチェーンでKZG検証が実行される, **Then** 検証が成功し `HoldingProved` イベントが発行される
3. **Given** 無効な証明（偽のシェア値）が提出された, **When** オンチェーンでKZG検証が実行される, **Then** 検証が失敗し `InvalidKzgProof` エラーが返される
4. **Given** ストレージノードがシェアを削除している, **When** チャレンジが発行される, **Then** ノードは応答できず、未応答としてカウントされる

---

### User Story 3 - 保持報酬の分配 (Priority: P2)

保持証明に成功したストレージノードに対し、報酬プール（投稿費用の90%が蓄積）から$moralトークンが報酬として分配される。報酬額は断片のデータサイズのみに基づいて計算される（スコアが閾値以上の場合のみ）。

**Why this priority**: ストレージノード運営者にインセンティブを与え、分散ストレージネットワークの持続可能性を確保する。

**Independent Test**: 保持証明成功後、ノードオペレーターのウォレット残高が増加することを確認。

**Acceptance Scenarios**:

1. **Given** ノードが保持証明に成功した（スコア閾値以上）, **When** 報酬計算が実行される, **Then** 報酬プールから `base_reward_per_byte × data_size` の$moralがノードオペレーターに付与される
2. **Given** 大きなデータサイズの断片を保持している, **When** 報酬が計算される, **Then** 小さなデータサイズの断片より高い報酬が付与される
3. **Given** 複数の断片を保持している, **When** 各断片の保持証明に成功する, **Then** 各断片ごとに報酬が累積される
4. **Given** スコアが閾値未満の投稿の断片を保持している, **When** 保持証明に成功する, **Then** 報酬は0となるが、証明成功の記録は残る
5. **Given** 報酬プールが枯渇している, **When** 報酬計算が実行される, **Then** 支払い可能な額のみが按分で分配される

---

### User Story 4 - スコア閾値による自然な忘却 (Priority: P2)

投稿のスコア（後に実装される外部システムが計算）が閾値を下回ると、その断片の報酬が0になり、ストレージノードにとって保持が経済的に不合理になる。自発的に削除され、3個未満のシェアになると復元不可能となり、投稿は「自然に忘却」される。

**Why this priority**: 「忘れられる権利」をスコアベースで実現。中央集権的な削除命令ではなく、コミュニティの評価（スコア）により分散的に忘却が実行される。

**Independent Test**: スコアが閾値を下回る状態をシミュレートし、一定期間後にシェアが取得不能になることを確認。

**Acceptance Scenarios**:

1. **Given** 投稿のスコアが閾値を下回る, **When** 次の報酬計算期間が到来する, **Then** その断片の報酬は0になる
2. **Given** 報酬が0の断片を保持している, **When** ノードのガベージコレクションが実行される, **Then** 経済的に不要な断片が削除候補となる
3. **Given** 3個未満のシェアしか残っていない, **When** 閲覧者が投稿を表示しようとする, **Then** 「このコンテンツは利用できなくなりました」と表示される
4. **Given** 投稿のスコアが閾値以上に回復する, **When** まだ3個以上のシェアが残っている, **Then** 断片の保持が継続され投稿は閲覧可能なまま

---

### User Story 5 - スコアベースの報酬制御 (Priority: P3)

外部スコアシステム（後に実装）が各投稿のスコアを計算し、閾値を超える投稿のみ報酬対象となる。報酬額はスコアではなくデータサイズのみに依存する。

**Why this priority**: スコアシステムは別機能として後に実装されるため、本機能ではスコアインターフェースのみを定義。

**Independent Test**: スコア閾値を設定し、閾値以上/未満の投稿で報酬が正しく切り替わることを確認。

**Acceptance Scenarios**:

1. **Given** 投稿のスコアが閾値以上である, **When** 報酬計算が実行される, **Then** データサイズに基づく報酬が付与される
2. **Given** 投稿のスコアが閾値未満である, **When** 報酬計算が実行される, **Then** 報酬は0となる
3. **Given** スコアシステムが未実装または利用不可, **When** 報酬計算が実行される, **Then** デフォルトスコア（閾値以上）が使用され、全投稿が報酬対象となる
4. **Given** 大きなデータサイズの投稿, **When** 報酬が計算される, **Then** 小さな投稿より高い報酬が付与される

---

### Edge Cases

- **シェアサイズ制限**: 1投稿あたりの最大データサイズ（32バイト × 多項式次数）を超えた場合 → 複数の多項式に分割
- **同時チャレンジ**: 同一ブロックで複数断片へのチャレンジが発生 → バッチ検証で効率化
- **ノード離脱中のチャレンジ**: オフラインノードへのチャレンジ → 猶予期間（600ブロック、約100分）後に未応答として記録
- **スコアシステム未接続**: スコア取得不可 → デフォルトスコア（閾値以上）を使用し全投稿を報酬対象とする
- **報酬プール枯渇**: 報酬プール残高が不足 → 支払い可能な額を按分で分配
- **KZGコミットメント不一致**: 登録時と異なるコミットメントで証明 → 即時拒否
- **Trusted Setup破損**: SRSファイルの整合性チェック → 起動時に検証
- **スコア境界付近**: スコアが閾値付近で変動 → ヒステリシスを適用し頻繁な切り替えを防止

## Requirements *(mandatory)*

### Functional Requirements

#### KZG-VSS (Wasm Engine)

- **FR-001**: System MUST sharksクレートをarkworksスタック（ark-bls12-381, ark-poly, ark-poly-commit）に置換する
- **FR-002**: System MUST BLS12-381曲線上で2次多項式を構成し、5個のシェアを生成する（`vss_split`、3-of-5構成）
- **FR-003**: System MUST Ethereum KZG Ceremonyの成果物（Trusted Setup）を埋め込み、コミットメント生成に使用する
- **FR-004**: System MUST 任意のシェアに対するKZG opening proofを生成できる（`vss_prove`）
- **FR-005**: System MUST 3個以上のシェアからLagrange補間により元データを復元できる（`vss_recover`）
- **FR-006**: System MUST 32KBまでのデータを単一の多項式でエンコードできる（1024個の32バイトスカラー）
- **FR-007**: System MUST 32KBを超えるデータを複数の多項式に分割して処理できる

#### Storage Pallet (オンチェーン)

- **FR-101**: System MUST `prove_holding_kzg` エクストリンシックを実装し、KZG proofを検証する
- **FR-102**: System MUST 各断片に対するKZGコミットメント（48バイト）を `Fragments` ストレージに保存する
- **FR-103**: System MUST チャレンジを生成し、ランダムに選択されたノードに保持証明を要求する
- **FR-104**: System MUST 証明成功時に `HoldingProved` イベントを発行する
- **FR-105**: System MUST 証明失敗または未応答をカウントし、3回連続で警告フラグを立てる
- **FR-106**: System MUST 外部スコアシステムから投稿スコアを取得するインターフェースを提供する（Trait or RPC）
- **FR-107**: System MUST 投稿スコアが閾値未満の場合、その断片の報酬を0とする
- **FR-108**: System MUST `claim_reward` エクストリンシックで保持証明成功ノードへの報酬支払いを実行する
- **FR-109**: System MUST 報酬計算式 `reward = base_reward_per_byte × data_size` を実装する（スコアが閾値以上の場合のみ）
- **FR-110**: System MUST スコアが閾値未満の断片を「忘却候補」としてマークする
- **FR-111**: System MUST スコア閾値をガバナンスまたはコンフィグで設定可能にする
- **FR-112**: System MUST スコアシステム未接続時にデフォルトスコア（閾値以上）を使用する
- **FR-113**: System MUST 投稿費用の90%を報酬プールに蓄積し、残り10%をバーンする
- **FR-114**: System MUST 報酬プールの残高をストレージ（`RewardPoolBalance`）で管理する

#### Storage Node (オフチェーン)

- **FR-201**: System MUST 保持するシェアに対してKZG proofを生成できる
- **FR-202**: System MUST チェーンからのチャレンジを監視し、自動的に証明を提出する
- **FR-203**: System MUST 報酬が0（スコア閾値未満）の断片を定期的にガベージコレクションする
- **FR-204**: System MUST ガベージコレクション前に7日間の猶予期間を設ける（設定可能、デフォルト7日）
- **FR-205**: System MUST 証明提出のスケジューリングを設定可能にする（例: 最大10件/ブロック）

#### Frontend

- **FR-301**: System MUST 投稿作成時にKZG-VSSでシェアを生成する（Web Worker）
- **FR-302**: System MUST 投稿閲覧時にシェアを収集し、Lagrange補間で復元する
- **FR-303**: System MUST 投稿の現在スコアを表示する（スコアシステム接続時）
- **FR-304**: System MUST スコアが閾値未満の場合、「忘却候補」の警告を表示する
- **FR-305**: System MUST スコアシステム未接続時はスコア表示を省略する
- **FR-306**: System MUST 投稿データを暗号化前に圧縮し、シェア分割後のデータサイズを削減する（256バイト未満のデータは圧縮スキップ）
- **FR-307**: System MUST シェア復元・復号後にデータを解凍し、元のコンテンツを表示する

### Key Entities

- **VssShare**: BLS12-381スカラー体上のシェア値（32バイト固定）。多項式 f(x) の評価値 f(i)。
- **KzgCommitment**: 多項式 f(x) に対するKZGコミットメント（G1点、48バイト）。
- **KzgProof**: 特定の点 i における評価値 f(i) の正当性を証明するopening proof（G1点、48バイト）。
- **RewardPool**: システム全体の報酬プール。投稿費用の90%が蓄積され、保持証明成功ノードに分配される。
- **ContentScore**: 投稿の評価スコア。外部システム（後に実装）から取得。閾値未満で報酬0。
- **ScoreThreshold**: 報酬対象となる最低スコア。ガバナンスまたはコンフィグで設定。
- **Challenge**: チェーンが発行する保持証明要求。断片ID、対象ノード、期限を含む。
- **ProofRecord**: 保持証明の成功/失敗記録。報酬計算と信頼度評価に使用。

## Assumptions

- Ethereum KZG Ceremony (Powers of Tau) の成果物は公開されており、自由に利用可能
- arkworksクレートはWasm（wasm32-unknown-unknown）ターゲットでビルド可能
- BLS12-381ペアリング計算はSubstrateランタイムで実行可能（または Off-chain Worker で実行）
- 報酬計算はブロックごとではなく、24時間ごとにバッチ処理
- ストレージノードは常時オンラインを前提とせず、猶予期間内に証明を提出できれば良い
- スコアシステムは別機能として後に実装される。本機能ではインターフェースのみ定義
- スコアシステム未接続時は全投稿が報酬対象（デフォルトスコア = 閾値以上）

## Out of Scope

| 機能 | 理由 |
|------|------|
| スコアシステムの実装 | 別機能として後に実装。本機能ではインターフェースのみ |
| スラッシング（ステーク没収） | 経済設計の複雑さ。Phase 3で検討 |
| 自己修復プロトコル | k-of-n設計の検討が必要。Phase 3で実装 |
| 閾値署名 | 別機能として分離 |
| 報酬のステーキング | 経済モデルの成熟後に検討 |
| 動的難易度調整 | 初期は固定パラメータで運用 |

## 技術的依存関係

```
arkworks (Wasm)
├── ark-ff (有限体)
├── ark-ec (楕円曲線)
├── ark-bls12-381 (BLS12-381実装)
├── ark-poly (多項式)
└── ark-poly-commit (KZGコミットメント)

Substrate (no_std)
├── sp-io::crypto (ホスト関数経由でKZG検証)
└── Off-chain Workers (重い計算のオフロード)

Ethereum
└── Powers of Tau (Trusted Setup成果物)
```
